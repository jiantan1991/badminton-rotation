# 羽毛球轮转 · 历史球局功能设计

日期：2026-08-08
状态：已确认

## 1. 需求

每次完整球局（一次活动，如"8月8日 12 场"）获得一个唯一 ID；
点"再来一局"时自动存档；用户可通过**历史列表**（日期+ID，点选）查看
之前任何一次球局的完整情况（名单、每场比分、最终排名）。

## 2. 关键决策

- **球局 = 一次完整活动**（非单个场次）
- **归档时机**：点"再来一局"时自动存档当前球局，成功后清空开新局
- **查看方式**：历史列表（自动列出日期+ID，点选查看），不做 ID 手动输入
- **存储方案**：服务器 `data/activities/<id>.json`（每球局一个文件，方案 A）
- **保留上限**：最多 200 条，超出自动删除最旧
- **历史只读**：不修改、不删除历史球局

## 3. 数据模型与 API（server.py）

### 存储结构
```
data/
├── activity.json              # 当前活动（现有，不变）
└── activities/                # 历史球局（每局一个文件）
    ├── 20260808-1930.json
    └── ...
```

### 球局 ID
`yyyymmdd-HHMM`（如 `20260808-1930`），服务器存档时自动生成。
同分钟冲突时追加序号：`20260808-1930-2`。

### 新增 API（仍零依赖）
| 接口 | 说明 |
|------|------|
| `GET /api/activities` | 历史列表，按时间倒序，最多 200 条。返回 `[{id, date, matchCount, complete}]` |
| `GET /api/activities/<id>` | 单个球局完整数据（activity 结构）。不存在返回 404 |
| `POST /api/archive` | body = 活动数据。生成新 ID 存档，返回 `{ok, id}`。超 200 条删最旧 |

现有 `GET/POST /api/activity`（当前活动）保持不变。

### 淘汰规则
存档后若 `activities/` 文件数 > 200，按文件名（时间序）删除最旧，直到 ≤ 200。

## 4. 前端

### 新增视图
1. **view-history（历史列表）**：设置页新增"📋 历史球局"入口按钮；
   列表行：`🗓️ 8月8日 19:30 · 12场 · 已完成/进行中`；点选进详情；"⬅ 返回"。
2. **view-history-detail（球局详情，只读）**：日期/ID/名单（强弱组）、
   每场比分完整列表（含胜负标记）、最终排名（复用 computeStandings）；"⬅ 返回列表"。

### "再来一局"流程（onRematch 改造）
```
点"再来一局"
  → 当前有活动？→ POST /api/archive（或本地存档）
  → 成功 → 清空数据 + 开新局
  → 失败 → toast"存档失败，请检查网络"，不开新局
```

### 本地降级（无后端，GitHub Pages/单文件版）
历史存 localStorage（key `badminton_history`，JSON 数组，上限 200），
同一套视图，仅本机可见。

## 5. 边界与错误处理

- 无历史 → "暂无历史球局"
- 超 200 条 → 自动删最旧（服务器与本地一致）
- 查看不存在 ID → "球局不存在"
- 存档失败 → 提示且不开新局（数据仍在当前活动，可重试）
- 历史详情只读

## 6. 明确不做（YAGNI）

- ❌ 修改/删除历史球局
- ❌ 搜索、分页（200 条列表足够）
- ❌ 球局自定义命名（日期时间即可）
- ❌ 历史球局的云同步双向合并（服务器模式即共享，本地模式仅本机）

## 7. 测试策略

- server.py：`/api/archive` 创建+ID、列表排序、200 上限淘汰、404、非法 ID
- 前端 DOM 桩：onRematch 存档调用时序、列表渲染、详情渲染、存档失败分支
- 浏览器端到端：打 1 场 → 再来一局 → 历史列表出现 → 点选查看比分/排名
